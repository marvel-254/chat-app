## Messaging security and threat model

**Do not advertise BRO as E2EE.** The old format used AES-GCM with a key derivable from participant IDs, and some sends silently stored plaintext. Both old forms were readable to a database operator or anyone with records and participant IDs. The historical GCM decoder is read-only, using the precise legacy derivation only for unversioned rows. These rows cannot be reliably split into old plaintext and damaged ciphertext, so if historical decoding fails, the original is preserved. New opted-in messages are marked `legacy_plaintext`; unknown formats are not rendered as content. Text, edits, attachments, voice notes, reactions, draft sync and scheduling are server-readable in the legacy mode. Users can read history without opting in. Opt-in is in memory per signed-in account and resets on logout or app restart. It is a client compatibility choice, not a database proof of informed consent; old clients predate it. Existing messages, queued drafts/schedules and files are not rewritten or deleted. Legacy scheduling still depends on a separate delivery worker; this PR does not add one.

A future secured transport must protect against malicious infrastructure, forged identity/session updates, corrupted or replayed envelopes and revoked devices. It cannot protect a compromised endpoint or a malicious/replaced web bundle that reads local secrets. Plan a separate protocol-native version with per-device verification, revocation, independently authenticated identity changes, protocol-managed replay protection and encrypted attachments (including captions/metadata when appropriate). Do not infer device trust from Supabase auth or backfill secure labels. Make offline scheduling and recovery explicit: never upload private keys or plaintext for a convenience feature. Server-visible metadata will still include routing, timing, and some traffic/size information. FCM, Supabase, and a TURN provider can see their respective delivery or transport metadata, but pushes do not contain names or message bodies. TLS and WebRTC DTLS-SRTP are not a verified end-to-end identity system.

## Calls and Recent Calls

`call_sessions` is the server authority. The RPC validates both members of an existing non-circle DM, checks blocks, serializes allocation, limits spam, and disallows transitions by outsiders. The callee atomically claims an answer; it sends readiness after subscribing and obtaining media. Offer/answer/ICE RPCs stamp sender and recipient and only broadcast to a private session topic. SDP and ICE are never put in history. Both clients poll during calls; the foreground coordinator polls for incoming calls across chats. A 45-second ring expires as missed/unanswered only if never accepted or otherwise terminated; accepting before expiry prevents missed notifications, even if media then fails. Connected time begins on an actual RTC connection. The server persists the first reported connected time and a terminal time; short reconnects are counted within the same elapsed call, and offline crash durations are estimates bounded by the last heartbeat/server deadline. A hangup the server never received cannot be distinguished from an abandoned ring. Terminal outcomes are immutable, and competing or delayed events do not produce a second history entry.

History is account-scoped, synchronized on reload and periodically while visible, with the latest 100 server records, per-account hide tombstones and 90-day server retention. Offline devices show their last cached metadata (platform secure storage; browser isolation still depends on origin security). Contact profiles refresh only online. Clear and remove require a connection and do not remove the peer's copy. No audio or video is recorded. Browser camera switch acquires the next camera then replaces only the existing video sender track; native switching reuses the plugin's camera capturer. No change to microphone, speaker or timer. Browsers/hardware that deny opening a second capture source keep the old camera and display an error. Debug call diagnostics contain state categories and retry counts, not IDs, SDP, IPs, or media.

### TURN configuration

Choose a measured regional deployment (include RTT from East Africa and mobile networks; evaluate latency, egress, quotas and support). Managed TURN offers regional availability and avoids host operations but needs billing and an adapter if credentials do not use coturn REST. The implemented integration uses coturn REST-compatible credentials. `docs/coturn.conf.example` is a starting point, not a hardened host build. Configure public DNS and TLS, TURN UDP/TCP 3478, TLS 5349 (optionally TCP 443 on a dedicated address), the relay port range, NAT mapping, egress blocks, monitoring and certificate renewal. Set Edge secrets `TURN_SHARED_SECRET` (same high-entropy secret as coturn) and `TURN_URLS` (comma-separated `turn:…?transport=udp`, `turn:…?transport=tcp`, `turns:…?transport=tcp`). The Edge function validates the Supabase user, applies a per-user issuance quota, and returns HMAC-derived one-hour credentials, never the shared secret. Rotate the shared secret in coordination with the TURN host; test before a rollout. No host or provider was provisioned. STUN fallback is available in ordinary builds; `CALL_RELAY_ONLY=true` fails closed if relay configuration is missing.

## Push deployment and privacy

Android uses the FCM token API and HTTP v1 `message.token`. FlutterFire 17 also exposes a separate FID direct-send API (`register` / `onRegistered`); these are **not interchangeable**. Old FID rows stay intact for migration/rollback but are not sent by the new worker. Upgrading and reopening an authorized client registers a fresh token row. Initial token, rotation, permission state/resume, local installation UUID, owner check, token uniqueness, logout deletion and FCM `UNREGISTERED` handling are wired. A device must reopen periodically (45-day idle registration retention). On a failed/offline logout, remote cleanup is best effort; subsequent account switch requires Firebase token invalidation before assigning the device to another account. OS notifications are generic regardless of device state. Settings permit per-account message/reminder and call preferences; sender and message previews are intentionally unavailable even for legacy messages.

Firebase Web Messaging uses the same HTTP v1 backend. Supply the Firebase Web app's public key, sender ID, app ID, project ID and **public** VAPID key via `.env.example`/deployment vars. Generate/import Web Push certificates in Firebase Console; the VAPID private key stays with Firebase. `scripts/build.sh web` generates the public `push-config.js` within `/app/`. The existing scoped service worker processes background data messages, uses a stable notification tag, and focuses/navigates an existing app tab or opens within scope. Flutter validates the recipient, current conversation membership, and the latest relevant call state before routing. A tab may reload on click. Require HTTPS (or localhost development), service workers, Push API, browser notification support and explicit permission from Settings. Test Chromium and Firefox; Safari/iOS and managed or private browsing depend on Firebase browser support, installed-PWA requirements and OS policy. Closing a tab differs from force-quitting a browser or Android app. Portables with disabled push still use foreground Realtime/polling.

The database queues event identifiers only. A periodic worker leases up to 32 records in parallel-safe batches; lease identity and a unique event/device key prevent concurrently processing the same delivery. Failed transient sends back off with jitter and `Retry-After`; invalid tokens are removed and permanent failures are discarded. No plaintext, tokens or peer identifiers go into batch logs. A worker crash after FCM accepts but before the DB records success is inherently at-least-once; tags and navigation dedup mitigate duplicate presentation, not exactly-once delivery. A delivered ringing alert can outlive a cancellation on the OS, but stale taps cannot answer and the terminal missed-call alert is only queued for a true final missed event.

## Migration, verification and rollback

1. Recover and verify **BRO** in the Supabase Dashboard, then make a database backup and compare `supabase migration list --linked`. Reconcile any older missing migrations before adding the three `20261120*` migrations. Use isolated Supabase staging for full `supabase db reset`, migration/RLS review, Realtime callback validation and the matrix above. The local PGlite harness runs the real new SQL/RLS against dependency stubs; it does not validate the complete hosted migration history, extensions or production configuration.
2. Confirm `pg_cron` (supports second-based schedules), `pg_net`, Vault, and Realtime private broadcasts work. Confirm the right Firebase Android app ID and that `google-services.json` matches the FCM project's HTTP v1 service account. Supply APNs credentials and entitlements for iOS if shipping. Set Edge secrets `FIREBASE_SERVICE_ACCOUNT_B64` (least-privilege service account JSON, base64), `PUSH_WEBHOOK_SECRET` (random), and both TURN secrets. The managed Supabase runtime supplies `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`; never provide the service role to clients. Set Vault `push_webhook_url` to the verified BRO project `push-new-message` function URL and `push_webhook_secret` to the exact same random secret. Confirm no old DB webhooks still deliver the same event. Do not paste secret values into shell history, logs or Git.
3. In a staged coordinated release, apply the migrations and deploy `call-turn` and `push-new-message` with config (`verify_jwt=false` for worker secret/explicit TURN auth). Test DB cron jobs/worker counts, Firebase sending and TURN-only calling before enabling the client. New messages require `content_format`; new calls and push registration require the new backend. Old client call signaling and old FID registration are not interoperable with new delivery. Update app stores/web builds together or announce the upgrade requirement. Pages and Vercel production builds must target BRO. Use a staging build with different credentials only on isolated staging, never the active unrelated project.
4. Roll back by stopping `bro-push-drain` in cron (retains queue for inspection), disabling selected push/relay deployments, and reverting clients to the last **truthful** security UI (do not restore claims of E2EE). If rollback of server endpoints is required, restore the previous verified function version/webhook shape and previous signaling policies only under reviewed operational controls. Prefer forward fixes; keep history, tombstones and content format data. Dropping migrations/tables would lose records and is not a routine rollback. Rotate TURN/FCM credentials if exposed and remove obsolete auth/configuration after cutover.
