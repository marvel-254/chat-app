# BRO private messaging, calls and push — release runbook

**Status: integration candidate, not an audited BRO release. Do not market all chats as E2EE.** The original AES-GCM keys could be computed from public participant IDs. A secure-storage cache and a TLS-protected private bucket do not change that. Old records and old clients are not secure. No live database, Firebase service account or relay was modified by this change.

## Trust model and protocol choice

Protect message and attachment contents from passive database, object-store, push and relay operators, network observers, users outside the conversation, and undetected alteration by storage. Trust an uncompromised client, OS key store, random source, delivered app code and an independent channel for comparing identities. The backend is trusted for membership, timely key revocation, scheduling and availability, **not** with a decryption key. A malicious directory can withhold devices or deny service. It must not be the source used to independently confirm the displayed fingerprints.

| Candidate | Decision |
|---|---|
| [libsignal](https://github.com/signalapp/libsignal) | Strong ratcheted sessions. Official Java/Swift and Node bindings do not constitute a supported Flutter/browser pair. AGPL licensing and another native/WASM binding would need review. |
| [vodozemac](https://github.com/matrix-org/vodozemac) / [Dart bindings](https://github.com/famedly/dart-vodozemac) | Audited Olm ratchets, Apache-2.0 core, viable future direction. Requires native Rust + a matching WASM build and a transactional per-device ratchet/prekey store. Do not improvise a Signal-like exchange. |
| [OpenPGP.js 6.3.2](https://github.com/openpgpjs/openpgpjs/tree/v6.3.2) | Selected: RFC 9580 sign-and-encrypt, interoperable packets, one library in both clients. [Upstream audit history](https://github.com/openpgpjs/openpgpjs/wiki/Cure53-security-audit) does **not** audit this version of BRO. LGPL-3.0+ bundle and license under `assets/crypto`; review LGPL distribution obligations for proprietary APK releases. |

Android uses a non-navigable, network-blocked WebView with an allowlisted local asset origin. Web loads the same bundle from its own HTTPS origin, not a CDN. Flutter secure storage holds a random per-installation **and per-account** private key; Android wraps storage with platform key protection (the OpenPGP signing key itself is not hardware-resident). In a browser, origin storage is not equivalent to Android Keystore: XSS, compromised hosting, extensions or profile access can compromise secrets. Clearing site data or reinstalling loses the key. No server escrow, automatic backups or history transfer. Non-Android native platforms have no v2 crypto adapter; sends fail closed.

Device registration publishes only the armored public certificate and its v6 fingerprint. Each conversation has an approved list of `(owner, fingerprint)` pairs in local secure storage. Open the shield on **every device**, compare each listed fingerprint to “this device” computed locally on that specific device over a separate authenticated channel, then approve. No shared public key or missing peer means no send. Addition, removal or replacement changes the list and blocks further sends pending comparison. Settings → Private message keys can revoke another device or rotate this one. A new install is a new identity, not a trusted continuation. Use “sign out other sessions” as well if session credentials may have leaked. Revoking prevents future encryption to that key; it cannot take back ciphertext or plaintext already delivered.

`bro2:<signing fingerprint>:<sorted recipient fingerprints>:<armored OpenPGP message>` is an application container, not a new cryptographic primitive. Each message has a fresh protocol-generated content key, wrapped to each registered device (including sender devices). OpenPGP authenticates the signed event version, sender, conversation, logical event UUID, recipients, purpose and reply target. The receiver verifies the pinned signing key and exact event context before exposing any plaintext. A unique event ID is reused on outbox retries. Duplicate insertion does not create a second message. Cross-row / cross-purpose replays fail; **a malicious database can suppress messages or roll a row back to a previously valid version**. There is no global ordering proof, double ratchet, post-compromise security or forward secrecy against later long-term private-key theft. There is no separate prekey server or session state to recover. Offline delivery works to previously enrolled devices.

Files use a fresh random 256-bit AES-GCM key and random 96-bit nonce per object. Only nonce + authenticated ciphertext are uploaded under an opaque blob filename. The key, MIME type, filename, size and path are inside the signed OpenPGP message. Image previews decrypt locally; other files can be explicitly saved on-device. Voice uses this same path, not a separate raw insert. File lengths, traffic timing, identities, device membership, reaction target, reply linkage, edit timestamps and call metadata remain visible. Local exports, UI screenshots/recordings by recipients and compromised endpoints are out of scope. Profiles, statuses, backgrounds, friendship timelines and public-facing media are **not** private-message content.

Drafts and pending outbox entries are local secure-storage data; the prior outbox is copied before its old preference is removed. Historical remote drafts remain readable, not rewritten. The old HKDF decoder lives only under `crypto/legacy.dart` for read compatibility; old plaintext and ambiguous unmarked base64 are labeled legacy. Unverified/revoked keys and failed envelope validation are distinct from legacy. No plaintext retry. Edit history is written transactionally; reactions and schedules use encrypted payloads. A signed-in sender client runs `deliver_my_due_messages` at startup, resume and roughly once per minute. Delivery requires a current verified device roster. Stale-roster schedules are retained rather than silently sent to revoked keys. Existing plaintext schedules are not auto-dispatched. There is no server-side content search, and no guarantee of exact-time delivery while the sender is offline. Retiring a key can make old versions unreadable; do not claim historical recovery. Audit this integration before release, particularly multi-tab key creation/rotation and deletion of reply targets.

## Calls and relay provisioning

Use `flutter_webrtc` 1.6.3 and Supabase private Realtime. `signal_call` derives `from` from `auth.uid()`, checks both users and a two-person conversation, limits signal size, and enforces ringing/accepted/terminal transitions. Client-originated inserts on the old call broadcast policy are removed. Room invite and per-call signaling channels are separate. An expiring invitation is durable; only current members who are parties may read it. A generic incoming push brings a recipient to the chat, which rechecks for a live invitation. Reject, busy, cancellation, setup deadline, lost connectivity, a bounded caller ICE restart and expired leases have distinct handling. A missed notification is not authority to start capture. Android starts the non-exported microphone/camera foreground service only after user-initiated media access. Force-stop cannot be bypassed. Incoming calls are **notification taps**, not full-screen telecom/CallKit calls. No claim of audited media identity against a malicious signaling server.

- Choose nearby managed relay capacity (usually bandwidth billing and regional redundancy) or maintain a public coturn host yourself (VM, egress, TLS, DDoS controls, patching and monitoring). Nairobi users should test actual relay RTT and throughput; this checkout provisions neither bandwidth nor a provider account.
- For coturn use `deploy/turnserver.conf.example`. Set public DNS, certificate/key, public IP and `external-ip=PUBLIC/PRIVATE` if behind NAT. Allow TCP/UDP 3478, TLS/TCP 443 and the configured UDP relay range both ways. Block all non-public peer destinations, cloud metadata and internal networks at the firewall including IPv6. Configure quotas and egress alerts.
- Generate a high-entropy secret (e.g. `openssl rand -base64 48`) **outside chat**, set the relay `static-auth-secret` and matching function `TURN_SHARED_SECRET`. Never put these in `.env.local`. `TURN_URLS` is a comma-separated list of TURN/TURNS URIs. Managed provider must support coturn-compatible REST HMAC credentials; a proprietary issuer is not interchangeable.
- The Edge Function validates the bearer with Auth, checks DM membership and a per-user/hour budget, then returns a random username with a one-hour expiry plus coturn HMAC-SHA1 password. No long-term credentials in the client; missing relay is a visible failure, not hidden STUN-only behavior. For long calls validate credential renewal/allocation lifespan in the chosen relay. Rotate shared secrets with an overlap window at least as long as issued credentials.
- Set public `CALL_RELAY_ONLY=true` for forced-relay tests. Diagnostic output is limited to category (relay/direct when selected stats are available), elapsed seconds and retry count. Do not collect raw stats, SDP, candidate addresses, audio, video or tokens. Do not enable request-body logging on the RPC or Edge path.

## Firebase, routing and Web Push

The pinned [FlutterFire 17.0.1 API](https://github.com/firebase/flutterfire/blob/firebase_messaging-v17.0.1/packages/firebase_messaging/firebase_messaging/lib/src/messaging.dart) **does** document registered FIDs. [FCM HTTP v1 discovery](https://github.com/googleapis/google-api-go-client/blob/main/fcm/v1/fcm-api.json) distinguishes `fid` and `token`. This branch explicitly uses `getToken` / `onTokenRefresh` / `deleteToken` and HTTP v1 `message.token` to meet the registration-token requirement. These token APIs are deprecated but supported in the pinned SDK; do not upgrade past removal without migrating both ends. Never populate token records from `FirebaseInstallations.getId()` or the old table.

1. Confirm the Android Firebase project and `com.omixsystems.pulsechat` app match the checked-in public `google-services.json`. Enable FCM HTTP v1 and give the sending service account only the required messaging permission. Supply its base64-encoded JSON as the **Edge-only** `FIREBASE_SERVICE_ACCOUNT_B64` (base64 is not encryption). The function exchanges a signed service-account JWT for a short-lived OAuth access token. Revoke old keys after rotation.
2. Register a **web** app in that same project; do not reuse the Android app ID. Generate/import a Web Push certificate in Firebase Cloud Messaging. Only the **public** VAPID key and public Web SDK settings go into `deploy/client.env.example`'s corresponding build variables. Firebase keeps the private key. HTTPS, notification permission, service workers, Push API and a supported FCM browser are required. Private browsing, OS restrictions and unsupported Safari configurations can prevent delivery; iOS typically requires an installed Home Screen app. A force-stopped browser is not guaranteed to wake.
3. User opts in from Settings → Enable message notifications. No web permission prompt on page load. Refresh on login/resume; on logout remove this account/install registration and invalidate its SDK token. Revoked permission and per-device refresh update the registry; stale rows expire after 60 days. A failed offline logout cannot recall in-flight generic notifications. Account and current membership checks are still mandatory before revealing anything. Devices not re-enrolled after cutover won't receive push.
4. Serve `service-worker.js` from the **app** scope (`/app/` or the Pages base path); pass that same relative path to FlutterFire. There should be just one worker for that scope. Do not redirect script requests to HTML or cache the worker forever. FCM data-only Web Push is handled even with no tab. Visible clients receive a local event, background clients a generic system notification with a stable tag. Clicks focus/post to an existing controlled tab or open the same-origin scoped shell with UUID parameters. Flutter checks auth, recipient AND live membership before navigation; it ignores arbitrary URLs and deleted chats. No backend endpoint allows arbitrary remote push URLs.
5. Backend resolves the triggering row and current recipients. Payload is routing IDs and generic text only. No chat body, filename, sender name or key in FCM. Optional sender/content previews decrypt **only inside the foreground app**, never on the lock screen; app/chat locks suppress them. Client Sentry export is disabled during rollout. Count-only Edge logging. Delivery uses bounded fanout, per-event/device leases, terminal invalid-token deletion guarded against refresh, and bounded exponential retries. Cron revisits failed pg_net jobs. Exactly-once delivery across a crash after FCM acceptance is impossible; stable message tags reduce visible duplicates. Monitor counts of exhausted `push_jobs` (`attempts=6`), not raw records. Correct provider configuration and replay a failed event within retention; do not redrive all successful deliveries.

On 2026-11-20 Supabase management listed **bro / zchsmnelvcuexchpwfgr / INACTIVE**. [Blocker #107](https://github.com/marvel-254/chat-app/issues/107). Never link, test or deploy against nyx. Recovery, backups and account/billing decisions belong to BRO's operator.

1. Run `supabase start && supabase db reset --local` on a Docker development machine; never reset a linked production project. Test the full historical chain and restore a disposable copy of BRO before rollout. Compare `supabase migration list --linked` with repo history. Take and verify backups; don't mark mismatches applied just to continue.
2. Enable Vault, pg_net, private Realtime and pg_cron. Apply the three `20261120…` migrations together in a coordinated client upgrade window. Old clients can read old conversations but their insecure sends/edits/drafts are rejected. Key registry is insert-only for its owner; co-participants can read **public** keys only. Endpoints are owner-only; delivery/relay state has no user-facing read policy. Service-role credentials never leave the backend. Historical messages/files are not deleted or upgraded by relabeling them.
3. After independently confirming BRO is healthy, `supabase link --project-ref zchsmnelvcuexchpwfgr`. Run `scripts/deploy-bro-backend.sh` (review dry run) then `scripts/deploy-bro-backend.sh --apply` only after staging passes. Populate the separate `deploy/functions.env.example` values via Supabase secrets. In Vault set `push_webhook_url` to BRO's `/functions/v1/push-new-message` and `push_webhook_secret` to the exact random value of Edge `PUSH_WEBHOOK_SECRET`. The webhook is internal-secret authenticated; TURN validates user JWTs. No webhook for an unrelated project. Verify cron jobs `bro-push-retry`, `bro-push-retention`, `bro-call-retention` exist; on tiers without cron arrange equivalent privileged scheduling.
4. Copy only `deploy/client.env.example` to `.env.local`; supply the BRO publishable key. Empty `CLOUD_STORAGE_URL` uses the private Supabase bucket. Existing R2 objects require the correct BRO-authorizing Worker, bucket and URL-signing secret; reconfigure/test it before enabling its explicit URL. An R2 bucket and a Supabase bucket are not interchangeable for historical paths. Set the same public inputs in Vercel/Pages/APK builds. Rebuild with `./scripts/build.sh web` / `./scripts/build.sh apk`. Do not reuse unrelated client URLs, export function env to builds, commit secrets or print push requests. Private attachments do not alter public profile media workflows.
5. Roll back by disabling webhook/relay issuance and pausing secure writes/call creation in a maintenance window. Keep ciphertext, device registry, media and old history. Roll forward with a compatible reader or restore the tested snapshot **to staging**. Do not downgrade clients to the plaintext writer or drop tables as an emergency rollback. Restore consistent app, worker and backend versions before resuming traffic. Rotate leaked secrets; revocation is not retroactive encryption.

## Validation and release gates

Run `flutter pub get`, `flutter analyze --no-fatal-infos --no-fatal-warnings`, `flutter test`, `flutter build web --release`, `flutter build apk --debug`; sign a release APK only in the release pipeline. `npm ci --prefix checks && node --test checks/*.test.cjs checks/*.test.mjs` runs the actual vendored crypto adapter, worker event tests and isolated PostgreSQL migrations/principal tests (PGlite, hosted-service fixtures). `deno check supabase/functions/{turn-credentials,push-new-message}/index.ts` and `deno test supabase/functions/push-new-message/delivery_test.ts` validate Edge code without live tokens. Unit success is **not** evidence of real FCM, TURN or production RLS behavior.

| Physical / staging test | Release criterion |
|---|---|
| Android A/B + browser C; compare primary fingerprints independently; add/replace/revoke C; send while B offline; lose local storage | No unapproved-device send; C cannot decrypt earlier messages; returns a clear failure, never plaintext; key replacement requires re-verification |
| Text/reply/edit/reaction/schedule/voice/image/document/GIF, wrong signer and altered object; legacy histories and cleared drafts | Inspect staging DB, object metadata and push transport for absence of plaintext/keys; check failed decryption, unchanged legacy records, account switch and offline outbox restart |
| Voice/video on same Wi-Fi, distinct Wi-Fi, LTE, restrictive NAT with direct disabled, UDP blocked/TLS 443, Wi-Fi↔LTE and brief outage | Confirm selected candidate category, media in both directions, bounded recovery or visible end; no indefinite ringing/connecting |
| Decline/busy/cancel, simultaneous answer on two devices, permissions denied, headset unplug/Bluetooth, lock/unlock, background/return, activity destroyed, 20 repeated calls | No lingering tracks/notification/timer; only one accept; after expiry no stale invite can start media |
| Android fresh install/login/refresh/reinstall; screen open/background/process killed; OS force-stop; no permission; token invalidation; account A→B | Correct token kind, one row per installation/account; verify invalid cleanup, generic lock-screen notification, correct authorized destination, no stack duplicates; document force-stop limits |
| Browsers with permission granted/denied/revoked, one/many tabs, closed tabs, offline retry, multiple profiles, unsupported browser and logout | No automatic prompt, no token on denial, safe focus/open, stale routes cannot disclose conversation; membership loss before click must deny |
| Duplicate webhook, provider 429/5xx, invalid token, loss after provider accept, missing secrets | Bounded retries, correct failure classification, idempotency, no retry storm or content in logs |

Independent crypto/application review, restored BRO staging, provisioned relay, real Firebase app/service credentials, and the physical-device matrix are outstanding release gates. The locally executable and CI suites are a starting point, not a certification.
